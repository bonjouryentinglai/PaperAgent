# Performance plan

Paper Agent keeps one Pi RPC process resident. Every answer waits for a complete
result before validation and writeback because the 100% to 60% layout preflight
must know whether the whole result fits or needs a native new page.

No latency claim should be published until it has been measured on a physical
Paper Pro Move. The current implementation should record these monotonic stages
during the next device session:

1. action accepted by the QMD
2. selection PNG first appears and becomes stable
3. request accepted by the resident oracle
4. prompt submitted to Pi
5. first assistant text received
6. complete model response received
7. native render complete
8. optional native page creation requested and acknowledged
9. primary pen acknowledged
10. first native ink or image insertion
11. final result complete

For each candidate, collect at least ten matched requests covering short Chinese
text, short English text, calculation, table, vector, Beautify text and Beautify
sketch. Compare median and slowest observed times as well as correctness.

## Optimization order

1. Keep Pi resident and thinking set to `off`.
2. Add stage timing before changing models, so network/model latency is separated
   from screenshot settling, Xochitl tool restoration, rendering and writeback.
3. A/B test `gpt-5.6-sol` and `gpt-5.6-luna` with identical selections. Luna is
   the first speed candidate, subject to the `openai-codex` provider actually
   exposing that model through the user's ChatGPT subscription.
4. Make the default plain answer deliberately short. OpenAI's latency guide says
   output generation is usually the largest latency step and that smaller models
   usually run faster.
5. Carefully overlap the initial primary-pen restoration with screenshot settling
   and tune the PNG stability interval only after measurement. These can remove
   fractions of a second, but must not reintroduce stale or partial screenshots.
6. Keep complete-result buffering for every output because neither the validator
   nor the adaptive layout policy can safely commit a partial answer before it
   knows whether the current page is usable.
7. Treat image latency separately. `gpt-5.6-luna` may speed classification and
   prompt preparation, but the raster itself is still generated by `gpt-image-2`.

OpenAI references:

- [Model catalog](https://developers.openai.com/api/docs/models)
- [Latency optimization guide](https://developers.openai.com/api/docs/guides/latency-optimization)

## Model routing constraint

The resident service currently launches one Pi process with one model. Running a
second process solely for per-action routing is a poor default on a 2 GB tablet,
while restarting Pi for every action would erase the warm-process latency gain.
The first experiment should therefore change the global model for one test run.
Dynamic per-request routing should be implemented only after Pi's RPC support and
memory cost have been verified on the Move.
